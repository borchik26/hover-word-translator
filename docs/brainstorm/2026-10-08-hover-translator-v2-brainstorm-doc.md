# Hover Word Translator v2

## What We're Building

Новая версия Tampermonkey-юзерскрипта (на базе `old_script.js`): при наведении курсора на английское
слово на любой странице поверх него появляется русский перевод, а оригинал под ним размывается.
Сейчас скрипт заранее оборачивает слова в `<span>` по захардкоженному словарю из ~600 слов (часть
ключей дублируется). Вместо этого v2 ищет слово под курсором в момент наведения и берёт перевод
из офлайн-словаря на десятки тысяч слов со словоформами и устойчивыми фразами. Словарь
собирается из Wiktionary (kaikki.org).

Работаем этапами:
1. **MVP (офлайн):** поиск слова по наведению, сборка словаря, адаптивный оверлей, меню вкл/выкл.
2. **API-фоллбэк:** Yandex Dictionary для слов вне словаря, кэш в `GM_setValue`.
3. **Омонимы:** показывать 2–3 значения с пометкой части речи вместо одного «угаданного».

## Why This Approach

**Поиск слова: по наведению, а не обёртка спанами.** Сейчас скрипт рекурсивно обходит DOM и
оборачивает каждое известное слово в `<span>`. Отсюда фризы на тяжёлых страницах (идея 3), слепота
к SPA и подгружаемому контенту (идея 1) и риск обработать узлы повторно (идея 4). Вариант с
`MutationObserver` + `WeakSet` + `requestIdleCallback` лечит симптомы, но добавляет кода и всё
равно ломает чужую вёрстку (выделение, копирование, React-гидрацию). Новый подход: на `mousemove`
с троттлингом `document.caretRangeFromPoint` (в Firefox `caretPositionFromPoint`) находит слово
под курсором, и над его `Range.getBoundingClientRect()` показывается один `position: fixed`
оверлей. DOM страницы не меняется, поэтому идеи 1, 3 и 4 **отпадают целиком**. Идея 7
(адаптивный CSS и выход за край экрана) решается расчётом координат.

**Словарь: сборка офлайн, в скрипт попадает только результат.** Дамп kaikki
(`kaikki.org-dictionary-English.jsonl`, 3.0 ГБ) нужен только на этапе сборки и в репозиторий не
коммитится. Python-скрипт `build/` вытаскивает из него русские переводы (`translations[]` с
`code: "ru"`, на уровне слова и на уровне значения), часть речи и формы (`forms`, `form_of`), а
затем оставляет только слова из топ-N частотного списка. На выходе компактный `dict.json`,
ожидаемо 2–5 МБ.

**Доставка: `@resource` с GitHub raw.** Tampermonkey скачивает ресурс один раз, хранит его в своей
внутренней базе и обновляет при смене `@version`. Отвергнуты:
- инлайн словаря в `.user.js`: многомегабайтный JS разбирается на каждой странице, редактор
  Tampermonkey с таким файлом тормозит;
- локальный `file://`: требует флага «доступ к URL файлов», а `GM_xmlhttpRequest` к `file://`
  запрещён;
- IndexedDB страницы: хранилище своё у каждого origin, копия на каждый сайт.

Верхняя граница по размеру: на `@resource` около 77 МБ Tampermonkey не загружается вообще
(issue Tampermonkey#1776). Наши единицы мегабайт далеко от неё.

встроен в один JS-объект, и поиск сводится к обычной выборке по ключу.

## Key Decisions

- **Поиск слова через caret API + один fixed-оверлей.** Убирает идеи 1, 3 и 4 и не трогает DOM страниц.
- **Словоформы (идея 6, частично) решаются в сборке, а не в рантайме.** Сборка раскрывает формы
  из kaikki (`went → go`, `leaves → leaf/leave`) в индекс `форма → лемма`, лемматизатор в
  скрипте не нужен.
- **Фразы (идея 8) тоже на этапе сборки.** Многословные статьи kaikki (`in order to`,
  `as well as`, `by the way`) попадают в отдельный индекс фраз. При наведении берём 1–3 слова
  вокруг курсора из того же текстового узла и сначала ищем самую длинную фразу.
- **Чистка словаря (идея 2) не нужна.** Хардкод-объект удаляется, источник истины — `dict.json`
  из сборки.
- **Доставка через `@resource` (GitHub raw) + `GM_getResourceText`.** JSON разбирается лениво, при
  первом наведении.
- **UI-настройки (идея 9): `GM_registerMenuCommand`.** Пункт «вкл/выкл на этом сайте», blacklist
  хранится в `GM_setValue`. `@match *://*/*` остаётся.
- **Адаптивный CSS (идея 7).** Цвета оверлея берутся из `prefers-color-scheme` (или
  нейтральный контрастный стиль), позиция ограничивается вьюпортом.
- **Этап 2.** Фоллбэк на Yandex Dictionary `lookup` через `GM_xmlhttpRequest` (CORS не мешает).
  Ключ API бесплатный, по ошибке `ERR_DAILY_REQ_LIMIT_EXCEEDED` (403) молча отключаемся до
  конца суток. Кэш ответов (идея 10) храним в `GM_setValue`: это хранилище расширения, общее для
  всех сайтов.
- **Этап 3.** Омонимы показываем как 2–3 значения с пометками (гл./сущ.), без угадывания POS
  по контексту.
- **Структура репо.** `src/` (скрипт), `build/` (Python-пайплайн), `dist/dict.json`
  (коммитится, на него ссылается `@resource`). Сам дамп kaikki в `.gitignore`.

## Open Questions

- **Размер N для частотного отбора** (30K? 50K?) и итоговый вес `dict.json`. Замерить на сборке.
  Решить, хранить ли один перевод или 2–3 с POS сразу, чтобы этап 3 не требовал пересборки.
- **Формат `dict.json`.** Объект `{word: "перевод"}` или более компактный (массивы и
  разделители), чтобы уменьшить вес и время `JSON.parse`. Замерить parse на ~3 МБ.
- **Качество переводов kaikki.** У частых слов бывают десятки переводов на разные значения. Нужно
  правило отбора 1–3 главных: первое значение, первый `ru` и т.д. Проверить вручную на ~50 частых
  словах; при плохом качестве подмешать FreeDict или Mueller.
- **Ресурсоёмкость сборки.** Потоковый разбор JSONL на 3 ГБ на ноутбуке: нужен построчный
  стрим, без загрузки в память целиком.
- **Публичный ли репозиторий на GitHub.** Raw-URL для `@resource` должен открываться без
  авторизации. Нужно проверить, что CC BY-SA (атрибуция Wiktionary) и лицензия FrequencyWords
  совместимы с публикацией `dict.json`.
- **Поведение оверлея.** Задержка перед показом (~150–300 мс?), что делать на тач-устройствах,
  нужно ли игнорировать `input`/`textarea`/`contenteditable` (скорее да).
- **Имена собственные и не-английские страницы.** Не показывать перевод для слов с заглавной
  буквы в середине предложения?
